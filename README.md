# AICoding Exam Playbook

一套面向 AICoding 笔试的中文解题手册，基于三次真实笔试经历持续修订。最新版本重点处理：如何利用最终评测反馈建立完整业务目标、怎样让 Task 与本地测试对应，以及如何定位多个 Task 组合后才出现的复杂业务失败。

> 这些内容来自有限实战样本，不代表所有 AICoding 平台遵循相同规则。仓库不会推测隐藏测试源码，只根据 README、公开测试、当前代码和考生实际取得的反馈推进。

## 最新方法

最新流程只保留两份辅助文档：

```text
spec.md：已知业务目标、Task、对应测试和已经确认的实现事实
debug.md：顽固场景的完整业务链、诊断证据、规则歧义和手动结果
```

主要过程是：

```text
README + 首次最终反馈
→ 建立当前已知的完整业务场景
→ 把场景划分成可验收 Task，并为每个 Task 规划测试
→ 分会话实现 Task，同时检查上游状态、共享数据和下游依赖
→ 考生手动运行本地测试和最终评测
→ 复杂失败先定位跨 Task 的第一个错误边界
→ 本地全链路通过后，才调查题面未写死的业务歧义
```

### 为什么不再使用 P0 和状态文档

“P0 业务”容易让 Agent 只提取主流程，把最终反馈中的异常、幂等、边界和跨实体联动合并进笼统功能。`AICODING_STATE.md` 也容易把业务规格变成进度记录。

最新版本改用 `spec.md` 保存业务行为合同，并要求每条已知最终反馈都有明确场景归属。代码存在、本地测试通过和最终平台验收通过始终作为三个不同事实处理。

### 为什么复杂测试要检查 Task 之间的接缝

当冒烟、基础和单点测试大多通过，只有两三个完整业务场景失败时，优先检查：

- 上游 Task 产生的状态是否满足下游 Task；
- 共享容量、占用、金额和余额是否漏更新、重复更新或释放错误；
- 主对象和关联对象是否同步；
- 失败不变、幂等、逻辑时间和 reset 是否在所有 Task 中一致；
- 单 Task 测试是否直接伪造中间状态，绕过了真实业务链。

只有本地完整业务链已经通过、平台仍报告同一场景时，才对一个具体的未确定规则建立 A/B 对照测试。

## 快速使用

1. 准备 README、全部业务代码和平台提供的原测试脚本。
2. 在开始实现前手动运行一次最终评测，复制全部已知业务场景。
3. 按 [最新 Prompt 手册](./09-AICoding场景驱动实战Prompt.md) 依次使用 Prompt 1–3。
4. 每个 Task 使用一个实现会话，并在同一会话中把已规划测试加入原测试脚本。
5. 手动运行测试，把真实命令和输出粘贴回对应会话；Agent 无法主动读取的结果不得预写为通过。
6. 最终仍有复杂场景失败时，根据 Prompt 4 的路由表选择一个具体诊断模块，不要同时猜测多个规则并批量改代码。

## 适用边界

- 本仓库是方法论与 Prompt 集合，不包含可运行的软件工程或自动验收工具。
- 最终评测反馈通常只提供业务场景名称，不能据此声称已经还原隐藏输入和断言。
- Agent 无法访问测试页面或用户终端时，必须由考生手动传递结果。
- 本地测试通过只能证明当前本地规则和实现一致，不能替代最终平台验收。
- 当前没有声明开源许可证；在许可证补充前，请勿默认获得复制、修改或再分发授权。
